- Migrations + seed: `npx prisma migrate deploy && npm run db:seed` run once
  inside that image against the dedicated Postgres (SEED_PASSWORD_* were
  throwaway local-only values, never printed here).
- App container: `docker run -p 18090:3000 ... habit-tracker-smoke-d2`.
- One deliberate difference from production, disclosed rather than hidden:
  ran with NODE_ENV=development (image default is NODE_ENV=production).
  backend/src/lib/session.ts sets the session cookie's `secure` flag to
  `process.env.NODE_ENV === "production"`; express-session's own documented
  behaviour is "If secure is set, and you access your site over HTTP, the
  cookie will not be set" - confirmed by testing both ways locally. Plain
  HTTP to localhost has no TLS, so with NODE_ENV=production no session
  cookie was ever returned and every login-dependent check failed at the
  first step. The real Cloud Run service serves over HTTPS, so this does
  not affect production; it is purely a local HTTP vs HTTPS artifact, not a
  code change (nothing under backend/ or deploy/release.sh was touched to
  get this local run working - only this run's own `docker run -e NODE_ENV`
  flag).
- One Manager-created template was needed as the "L7-CHECK*" fixture this
  script looks for (the script only ever logs in as Participants, per the
  design decision to keep SMOKE_EMAIL/SMOKE_PASSWORD as participant 1
  unchanged): created once by hand via curl as manager@example.com,
  named "L7-CHECK-LOCALVERIFY" (minValue=0, maxValue=50), landing at
  template id 1 in this fresh database.
- SMOKE_L7_GOAL_ID (new env var, default 12 - the real deployed fixture's
  goal id from docs/labs/lab-07/evidence/post-deploy-check-output.txt) was
  left at its default for the main runs below, which is why
  PERSIST-LAB7-GOAL/PERSIST-LAB7-ENTRIES correctly report "not found": a
  fresh local database has no goal 12 at all, let alone one with the real
  Lab 7 entry dates. This is the expected, disclosed local-environment
  limitation named in the script's own module docstring - not a defect in
  the script or the app. The real deployed environment has the real
  fixture at that id; see the post-deploy run for that check actually
  passing.
- Local python3 is 3.8 (no `zoneinfo`, stdlib since 3.9); used
  /Library/Frameworks/Python.framework/Versions/3.9/bin/python3 (3.9.6) for
  this local run only. The deploy workflow's own Python is 3.14
  (actions/setup-python, .github/workflows/deploy.yml), so this is a local
  machine difference, not a script compatibility issue.
